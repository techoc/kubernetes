# 构建、测试、验证工作流

## 1. 命令路由

| 命令 | 实际脚本 | 副作用 |
| --- | --- | --- |
| `make help` | `hack/make-rules/make-help.sh` | 只打印目标帮助；无 `TERM` 时用 `TERM=xterm make help` |
| `make` / `make all WHAT=...` | `hack/make-rules/build.sh` | 构建二进制到输出目录 |
| `make test WHAT=...` | `hack/make-rules/test.sh` | 跑单测；可写 JUnit / coverage 产物，不改业务源码 |
| `make test-integration WHAT=...` | `hack/make-rules/test-integration.sh` | 启动 etcd，再递归跑 integration 测试 |
| `make test-e2e-node` | `hack/make-rules/test-e2e-node.sh` | 启动节点测试；需要 Linux 与权限前置 |
| `make test-cmd WHAT=...` | `hack/make-rules/test-cmd.sh` | 启动本地控制面，跑 `test/cmd` 脚本 |
| `make verify` | `hack/make-rules/verify.sh` | 扫描并执行 `hack/verify-*.sh` / `.py`，以检查为主 |
| `make quick-verify` | `hack/make-rules/verify.sh` | 只跑 `QUICK_PATTERNS` 中的快检查 |
| `make update` | `hack/make-rules/update.sh` | **会改仓库文件**，运行生成器与格式器 |

`Makefile:50` 的 `.EXPORT_ALL_VARIABLES` 把 `WHAT`、`GOFLAGS`、`KUBE_TEST_ARGS` 等传给脚本。`Makefile:208` 把 `KUBE_TEST_ARGS` 显式转给 `test-integration.sh`，保留美元符号与 shell 引用。

## 2. 单元测试

```bash
make test WHAT=./pkg/registry/core/pod GOFLAGS=-v
KUBE_TEST_ARGS='-run ^TestPodStrategyValidate$' make test WHAT=./pkg/registry/core/pod GOFLAGS=-v
make test WHAT=./pkg/kubelet GOFLAGS=-v KUBE_COVER=y
```

`hack/make-rules/test.sh` 的默认值：

- `KUBE_CACHE_MUTATION_DETECTOR=true`
- `KUBE_PANIC_WATCH_DECODE_ERROR=true`
- `KUBE_RACE=-race`
- `KUBE_TIMEOUT=-timeout=180s`

不带 `WHAT` 时，脚本通过 `go list -find` 枚举 workspace 中含测试文件的包，排除 `test/e2e*`、`test/integration`、`third_party` 等，最终经 `gotestsum --raw-command -- go test -json ...` 执行。学习阶段永远优先带 `WHAT`，否则全仓库单测会吃掉整个下午。

## 3. 集成测试

```bash
make test-integration WHAT=./test/integration/scheduler
make test-integration WHAT=./test/integration/pods GOFLAGS=-v KUBE_TEST_ARGS='-run ^TestPodUpdateActiveDeadlineSeconds$'
```

`hack/make-rules/test-integration.sh`：

- 要求 PATH 中有 etcd；缺则先 `hack/install-etcd.sh`
- 启动并清理 etcd
- `KUBE_TIMEOUT=-timeout=600s`
- `KUBE_PANIC_WATCH_DECODE_ERROR=false`
- 把 `WHAT` 缺省为各模块的 `test/integration/...` 包
- 给 `KUBE_TEST_ARGS` 追加 `-short=true --vmodule=...`，再递归 `make ... test`

注意 `test-integration.sh` 正文没有直接消费位置参数 `$@`，选择范围依靠导出的 `WHAT` 环境变量。写命令时显式带 `WHAT=...`，别只把目录放在命令行尾部然后期待 shell 自己读心。

## 4. verify

```bash
make verify WHAT="boilerplate gofmt test-code typecheck"
make quick-verify
make verify
```

`WHAT` 的值是检查脚本名去掉 `verify-` 前缀与扩展名，例如 `gofmt` 对应 `hack/verify-gofmt.sh`。`hack/make-rules/verify.sh` 会扫描根目录与各 staging 模块中的 verify 脚本，排除若干 CI 专用 / 会造成递归的脚本。结果通过 shell2junit 写到 `${KUBE_JUNIT_REPORT_DIR:-/tmp/junit-results}`。

与学习最相关的检查：

| 检查 | 脚本 | 作用 |
| --- | --- | --- |
| `boilerplate` | `hack/verify-boilerplate.sh` | 校验 license header |
| `gofmt` | `hack/verify-gofmt.sh` | 格式 |
| `codegen` | `hack/verify-codegen.sh` | 生成物与输入一致 |
| `featuregates` | `hack/verify-featuregates.sh` | Feature gate 文档 / 生命周期数据一致 |
| `openapi-spec` | `hack/verify-openapi-spec.sh` | OpenAPI 规格一致 |
| `generated-docs` | `hack/verify-generated-docs.sh` | 生成文档一致 |
| `import-boss` | `hack/verify-import-boss.sh` | 包依赖方向 |
| `typecheck` | `hack/verify-typecheck.sh` | 类型检查 |
| `vendor` | `hack/verify-vendor.sh` | vendor / go.mod 一致 |
| `readonly-packages` | `hack/verify-readonly-packages.sh` | 只读包边界 |
| `test-code` | `hack/verify-test-code.sh` | 测试代码约束 |

`verify-codegen.sh` 一类检查通过 `hack/lib/verify-generated.sh` 在干净临时 worktree 跑对应 update 脚本并检查 diff，因此需要干净工作树或可复现的临时副本。不要手动把 `hack/verify-all.sh` 当总入口；`verify.sh` 明确排除它以避免递归。

## 5. update

```bash
git status --short
make update SILENT=false
git diff --stat
```

`make update` 默认 `SILENT=true`，失败即停；`FORCE_ALL=true` 会强制跑完所有脚本。`hack/make-rules/update.sh:38` 的 `BASH_TARGETS` 当前是：

1. `hack/update-codegen.sh`
2. `hack/update-featuregates.sh`
3. `hack/update-generated-api-compatibility-data.sh`
4. `hack/update-generated-docs.sh`
5. `hack/update-openapi-spec.sh`
6. `hack/update-gofmt.sh`
7. `hack/update-golangci-lint-config.sh`

这会重写生成代码、Feature gate 参考数据、文档、OpenAPI spec、格式与 lint 配置。`hack/update-openapi-spec.sh` 还会临时启动 kube-apiserver + etcd 抓取规格。运行前检查工作树，运行后检查 `git diff`，别把生成器输出误认为“顺手格式了一下”。

## 6. generated files

- 禁止手改：`zz_generated.*`、`generated.pb.go`、带 `Code generated by ... DO NOT EDIT.` 的文件
- 修改输入：API 类型 / `+k8s:` tag / proto / feature gate 定义 / 文档源
- 重新生成：`make update`，或对应 `hack/update-*.sh`
- 检查一致性：对应 `make verify WHAT=...`，最终跑全量 `make verify`
- 生成器源码：`staging/src/k8s.io/code-generator/cmd/`

典型映射：

| 输入 | 产物 |
| --- | --- |
| `staging/src/k8s.io/api/core/v1/types.go` + tags | `zz_generated.deepcopy.go`、clientset、listers、informers、applyconfigurations |
| `pkg/apis/core/v1` defaults / conversion | `zz_generated.conversion.go`、`zz_generated.defaults.go`、`zz_generated.validations.go` |
| `staging/src/k8s.io/cri-api/.../api.proto` | `api.pb.go` |
| OpenAPI 标注与 API 类型 | `api/openapi-spec/swagger.json`、`pkg/generated/openapi/zz_generated.openapi.go` |
| `pkg/features/kube_features.go` | `test/compatibility_lifecycle/reference/` 等 Feature gate 数据 |

## 7. 依赖

```bash
hack/pin-dependency.sh <module> <sha-or-tag>
hack/update-vendor.sh
```

`hack/pin-dependency.sh` 修改根模块与 staging 模块里的版本声明，并提示随后运行 `hack/update-vendor.sh`。后者重写 `go.mod` / `go.sum` / `go.work` / `go.work.sum`、`vendor/` 与 `vendor/LICENSES`。`go.mod` / `go.work` 是生成文件，禁止 `go mod tidy`。

## 8. 本地集群与 E2E

- 本地控制面：`hack/local-up-cluster.sh`，Linux 上可能需要 root 与容器运行时
- 集群 E2E 构建：`make WHAT=test/e2e/e2e.test`
- 集群 E2E 运行：`hack/ginkgo-e2e.sh`，需要已部署集群和 kubeconfig
- 命令行测试：`make test-cmd WHAT="deployment impersonation"`
- 节点测试：`make test-e2e-node FOCUS=... SKIP=...`，见 `test/e2e_node/README.md`
- Conformance：`test/conformance/README.md`、`hack/verify-conformance-yaml.sh`、`hack/update-conformance-yaml.sh`

学习顺序：先单元 → 定向 integration → 读 E2E 框架 → 有集群再跑 E2E。先跑全量 E2E 通常只会得到一堆环境错误和少量知识。

## 9. 推荐日常回路

```bash
git status --short
make test WHAT=./pkg/registry/core/pod GOFLAGS=-v
make verify WHAT="boilerplate gofmt test-code typecheck"
# 涉及生成输入时：
make update SILENT=false
git diff --stat
make verify
```

`make verify` 放最后，不是因为它不重要，而是因为它会认真检查你前面所有的侥幸。
